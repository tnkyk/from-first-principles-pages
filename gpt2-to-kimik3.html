GPT-2 から KimiK3 まで, from First Principles

原著: ali (@waterloo_intern) — «22580: From GPT2 to Kimi3, Explained»。図とコードは原文のまま。本文は、注意深い非専門家でも一歩ずつ追えるよう説明を組み直した日本語。

2万2580。

2019年の GPT-2 を、2026年の KimiK3 の中に何個ぶん詰め込めるか、という数え方だ。パラメータの量だけで見ると、7年でおよそ2万2580倍に膨らんだ。

だが、大きくなっただけなのだろうか。中身の組み立て方は、同じまま大きくなったのか。

この記事は、原著のワークログを日本語で辿るものだ。出発点の GPT-2 から、Linear Attention、DeltaNet、ゲート、Kimi Linear、そして KimiK3 まで。

追うのは部品のカタログではない。「覚える場所が足りない」「古さが混ざる」「まとめて計算できない」——そのたびに何を足し、何を捨てたか、を一つずつ確かめる。

GPT-2

まず出発点を固定する。GPT-2 は、すでに出た語だけを見て次の語を出す、デコーダ専用の形だ。翻訳のように「入力文を別経路で読む」エンコーダは持たない。チャットで見慣れた「左から右へ一文を伸ばす」機械の、小さな原型だ。

tok_emb = self.transformer.wte(idx) # token embeddings of shape (b, t, n_embd)
pos_emb = self.transformer.wpe(pos) # position embeddings of shape (t, n_embd)
x = self.transformer.drop(tok_emb + pos_emb)
for block in self.transformer.h:
    x = block(x)
x = self.transformer.ln_f(x)
logits = self.lm_head(x)
return logits

入力の最初の仕事は、記号を数の列にすることだ。各トークン（語の断片）に埋め込みベクトルを割り当て、さらに「何番目か」を表す位置の埋め込みを足す。ここまでで、モデルは文字ではなく、位置つきのベクトル列を見る。

その列は、同じ形のブロックを何度も通る。一つのブロックを拡大すると、だいたい次の二段になる。先に注意（どれをどれへ混ぜるか）を足し、次に MLP（位置ごとの変換）を足す。どちらも、入ってきたものに「差分」として足し戻す残差の形だ。

class Block(nn.Module):
    def __init__(self, config):
        super().__init__()
        self.ln_1 = LayerNorm(config.n_embd, bias=config.bias)
        self.attn = CausalSelfAttention(config)
        self.ln_2 = LayerNorm(config.n_embd, bias=config.bias)
        self.mlp = MLP(config)

    def forward(self, x):
        x = x + self.attn(self.ln_1(x))
        x = x + self.mlp(self.ln_2(x))
        return x

注意の中身は、ざっくりこう読む。いま見たい位置がクエリ（Q）、参照される側がキー（K）とバリュー（V）。Q と K の相性で重みをつけ、その重みで V を混ぜる。未来の語はまだ見えないので、後ろはマスクで隠す。

        B, T, C = x.size() # batch size, sequence length, embedding dimensionality (n_embd)

        # calculate query, key, values for all heads in batch and move head forward to be the batch dim
        q, k, v  = self.c_attn(x).split(self.n_embd, dim=2)
        k = k.view(B, T, self.n_head, C // self.n_head).transpose(1, 2) # (B, nh, T, hs)
        q = q.view(B, T, self.n_head, C // self.n_head).transpose(1, 2) # (B, nh, T, hs)
        v = v.view(B, T, self.n_head, C // self.n_head).transpose(1, 2) # (B, nh, T, hs)

        # manual implementation of attention
        att = (q @ k.transpose(-2, -1)) * (1.0 / math.sqrt(k.size(-1)))
        att = att.masked_fill(self.bias[:,:,:T,:T] == 0, float('-inf'))
        att = F.softmax(att, dim=-1)
        att = self.attn_dropout(att)
        y = att @ v # (B, nh, T, T) x (B, nh, T, hs) -> (B, nh, T, hs)
        y = y.transpose(1, 2).contiguous().view(B, T, C) # re-assemble all head outputs side by side

        # output projection
        y = self.resid_dropout(self.c_proj(y))
        return y

最後の隠れ状態がそろうと、言語モデルヘッドが「語彙のどれが次か」のスコア（ロジット）へ写す。一文を伸ばすとき——自己回帰デコード——実際に次の一語を選ぶのに使うのは、いちばん新しい位置のスコアだけだ。前の位置のスコアも計算しているが、その一歩では使わない。

ここに、デコーダ専用生成のむだが見える。モデルは入力のすべての位置の表現を作るのに、デコードの一歩が飲むのは最後の位置のスコアだけだ。キャッシュがなければ、次の語を出すたびに、これまでの計算の多くをやり直すことになる。

KV キャッシュは、そのむだへの素直な答えだ。新しい語を付け足したあと、過去トークンのキーとバリューを毎回いちから作り直す必要はない。一度出した K と V を取っておけば、同じ射影を繰り返さずに済む。

その保管庫が KV キャッシュだ。これまでの N−1 個ぶんのベクトルを抱え続ける。文が長くなるほど倉庫は太り、やがて「計算そのもの」より「メモリから運ぶ速さ」が詰まりうる。

大きさの感覚だけ先に置く。語彙はおよそ5万、ブロック12、ヘッド12、埋め込み次元768。この GPT-2 サイズのベースラインは、およそ1億2400万パラメータだ。

n_layer: int = 12
n_head: int = 12
n_embd: int = 768

Linear Attention

普通の Softmax Attention は、Q と K を掛けたあとで非線形（指数）をかけ、すべてのクエリをすべてのキーへ結びつける。系列が長いほど、この結びつきの表は縦にも横にも伸びる。

Linear Attention は発想を変える。ELU+1 のような写像を、Q と K に別々に先にかけておく。すると掛け算の順番を組み替えられ、増え続ける K と V を、長さに依らない固定サイズの D×D の状態へ畳み込める。「全文の表」ではなく、「要約されたメモ一枚」で済む、というイメージだ。

原著の著者は、論文の「コストが系列長の二乗」という言い方に一度つまずいている。いまの実装感覚では、Flash Attention がその二乗の実体化をかなり和らげた、と思いやすい。だがその論文は2020年。いま読んでいる Linear Attention の文脈より前の世界の話だ。

当時の訓練では、N×N の注意行列をそのままメモリに広げがちだった。FlashAttention はまだなく、参考実装は KV キャッシュなしで履歴を再計算することも多かった。「長いほど重い」は、机上の話ではなく、当時の実装の感触でもあった。

def forward(self, x, mask=None, past_kv=None):
  # x is b,t,d
  b,t,d=x.shape
  d_head=d//self.num_heads
  h=self.num_heads
  qkv=self.qkv_proj(x)

  q=qkv[:, :, :d].view(b,t,h,d_head).transpose(1,2)
  k=qkv[:, :, d:2*d].view(b,t,h,d_head).transpose(1,2)
  v=qkv[:, :, 2*d:].view(b,t,h,d_head).transpose(1,2)

  # at prefill, q,k,v have shapes b,h,t,d
  # at decode, shape is b, h, 1, d
  # so i cat at the t dimension, dim(2)

  if past_kv is not None:
    k_past=past_kv[0]
    v_past=past_kv[1]
    k=torch.cat((k_past, k), dim=2)
    v=torch.cat((v_past, v), dim=2)

  scores=(q@k.transpose(-1,-2))/math.sqrt(d_head)
  if past_kv is None: #we're in prefill and need to mask
    causal_mask=torch.ones(t,t,dtype=bool, device=q.device)
    causal_mask=torch.triu(causal_mask, diagonal=1)
    scores=scores.masked_fill(causal_mask, float('-inf'))

  if mask is not None:
    scores=scores.masked_fill(~mask, float('-inf'))

  #get attn (bhtt x bhtd)
  attn=scores.softmax(-1)#bhtt
  o=attn@v #bhtd
  o=o.transpose(1,2).contiguous().view(b,t,d)  #b,t,d

  # use x to get qkv
  o_proj=self.o_proj(o)
  past_kv=(k, v)
  return o_proj, past_kv

読み書きが多すぎる。Linear Attention 側の論文は、そこを次のような更新に置き換える。毎回の巨大な履歴テーブルではなく、固定サイズの状態を足し更新していく。

ただし、楽になる代わりに失うものがある。

Softmax が使う指数の代わりに、相互作用の前に Q と K へ別々へ ELU+1 をかける。どちらもあとで割り算して重みをそろえるが、Linear 側の写像は Softmax の近似としては表現力が弱い。忠実度は落ちうる。実務でどれだけ精度が落ちるかは、設計と仕事内容次第だ。

ちなみに、QK の和で割る正規化は今も行う。図では単純化のため省略されているだけだ。高レベルでは、注意は次の三手に分解できる。

  1. スコアを非負にする。Linear は ELU+1、Softmax は指数。
  2. 和で割り、重みをそろえる。
  3. その重みでバリューを混ぜる（加重平均）。

注意という契約——「相性で重みをつけ、値を混ぜる」——は保たれる。ただ、非負にする手段が弱い近似になっている。

DeltaNet（Fast Weight Programmers）

固定サイズのメモには、置く場所が限られる。新しいトークンの情報は、専用の引き出しをもらえない。同じ D×D の一枚に、足し込まれていく。

すると困ることが起きる。あとから「あのとき書いた事実だけ」を、きれいな孤立状態では取り出せなくなる。前のインクの上に、新しいインクが重なるからだ。

その加算こそが、長さに比例して太らない理由でもある。履歴を後ろへ連結する代わりに、同じ板へ足す。効率は上がるが、情報が干渉する。DeltaNet が狙うのは、この「取り出しにくさ」への対処だ。

Schlag の論文（Fast Weight Programmers）は、この限界をはっきり書いている。

「系列長が記憶容量を超えると、過容量の状態に入りうる。そこでは、何を残し何を消すかを選びながら記憶とやり取りする必要がある。ただ足し続けるだけの命令では足りない。有限の記憶へ連合を終わりなく足せば、いずれ限界に達する。」

Linear Attention が魅力的なのは、系列長 N が状態の幅 D よりずっと長いときだ。同じ条件が、弱点もむき出しにする。更新が加算だけで、何も出ていかないなら、容量を超えた連合は互いに邪魔をし始める。

def forward(self, x, mask=None, cache=None):
  # x is b,t,d
  b,t,d=x.shape
  d_head=d//self.num_heads
  h=self.num_heads
  qkv=self.qkv_proj(x)

  q=qkv[:, :, :d].view(b,t,h,d_head).transpose(1,2)
  k=qkv[:, :, d:2*d].view(b,t,h,d_head).transpose(1,2)
  v=qkv[:, :, 2*d:].view(b,t,h,d_head).transpose(1,2)

  q = F.normalize(F.silu(q), dim=-1)     
  k = F.normalize(F.silu(k), dim=-1)     
  beta = torch.sigmoid(self.w_beta(x)).view(b, 1, t, 1)   
  # new: per-token write strength

  S = cache if cache is not None else 0.0  

  v_old = k @ S # read the board at this key
  u = beta * (v - v_old) # the delta: only what's actually new
  S = S + k.transpose(-1, -2) @ u # same outer-product write as before

  o = q @ S # read, no denominator
  o = o.transpose(1, 2).contiguous().view(b, t, d)
  return self.o_proj(o), S

数式より先に、小さな操作の絵で追う。

一つの連合を、ごく単純に S = kᵀ @ v と書く。同じキー k で読み戻すと、k @ (kᵀ @ v) になり、結局「k の長さの二乗」倍の v が返る。

つまり読み出しは、キーの大きさで伸び縮みする。k を長さ1にそろえるか、あとでその大きさで割れば、v をそのまま取り戻せる。「書いたものを、同じ鍵で開ける」最小の例だ。

クエリ Q も、学習されたポインタだと思える。Q 用と K 用の射影は同じ残差の流れを読み、ある事実を思い出したいときの Q は、その事実を書いた K の方向を指す。

Delta の更新は、だいたい次の順だ。いまのキーで、板（キャッシュ）から何が読めるかを見る。書きたい値から、その既読ぶんを引く。差分だけをキーに載せて足し戻す。古いインクを消し、新しいインクを同じ場所へ書く——上書きに近い操作になる。

DeltaNet（並列化）

ここがいちばん難しい。原著の著者も、手応えのある理解までおよそ7時間かかったと書いている。なので、抽象より実装の順で組み立てる。

短い要約だけ先に置く。DeltaNet は、一歩前の状態から一歩後の状態へ進む一次の線形再帰だ。遷移の仕方をうまく書き直すと、系列を長さ C の塊（チャンク）に分け、塊ごとにある程度まとめて前へ進められる。訓練で「一トークンずつしか進めない」壁を下げ、ハードウェア向きの線形時間に近づける、という話だ。

実務で痛いのは、長いプロンプトを最初に飲み込む段階——いわゆる prefill——だ。T 個のトークンへ Delta 規則をそのまま書くと、次のような一歩ずつのループになる。

S = torch.zeros(b, h, dh, dh) if cache is None else cache
outs = []
for i in range(t):
    k_i = k[:, :, i:i+1]  
    v_i = v[:, :, i:i+1]
    b_i = beta[:, :, i:i+1]
    v_old = k_i @ S                  
    u_i  = b_i * (v_i - v_old)
    S = S + k_i.transpose(-1, -2) @ u_i # write
    outs.append(q[:, :, i:i+1] @ S)

普通の注意と違い、キーのたびに「今ある状態からの補正」が要る。だから、いきなり大きな行列の掛け算一発、には見えにくい。Delta を外しても、素朴な Linear Attention の prefill は、状態を順に更新する逐次処理のままだ。

そこで系列をチャンクに切る。塊の中と、塊と塊のあいだで、やり方を分けるとうまくいく。図の例で追うのがいちばん早い。

チャンク長 C を系列長 N と同じにすると、いつもの O(N²) Attention に戻る。C=1 にすると、普通の Linear Attention になる。そのあいだの C は、塊の中で少し余分に計算する代わりに、GPU が得意な大きさの行列積へ仕事を載せる。実務では C は64や128が多い。テンソルコアが効きやすい粒度だからで、UMMA はその一例だ。

塊の中でできた中間結果は、状態 S の更新へ折り込まれる。

S = torch.zeros(b, h, dh, dh) if cache is None else cache
outs = []
for i in range(t//C):
    q_c = q[:, :, i*C:(i+1)*C]  
    k_c = k[:, :, i*C:(i+1)*C]  
    v_c = v[:, :, i*C:(i+1)*C]

	  o_prev=q_c@S #this is everything up to this block
	  
	  attn=(q_c@k_c.transpose(-1,-2)).tril() #masked attention 
	  o_curr=attn@v_c
		  
		o=o_prev+o_curr
    
    S_new=k_c.transpose(-1,-2)@v_c #recurrent attention 
    S=S+S_new
    outs.append(o)

o = torch.cat(outs, dim=2)

塊の中では、普通の注意と同じ順——まずスコア、マスクあり——で q(kᵀv) をやる。塊と塊のあいだでは順が逆で、(kᵀv) を先に状態へ折り、あとで q で読む。再帰的に「要約メモを更新してから読む」順だ。

全体の注意表が N² で膨らむ普通の Attention と違い、ここはそうならない。コストは二つに分かれる。状態まわりの固定費（だいたい 2Ld²。C に依らない）と、対角に並ぶ塊内スコアの成長費（だいたい 2LCd）だ。C を L と同じにすると後者が 2L²d になり、いつもの二乗に戻る。C を小さくするほど計算量の個数（FLOPs）は減る。

ただし FLOPs が最少だから壁時計でも最速、とは限らない。GPU は、行列積ユニットにうまく載る形の仕事のほうが、個数が多くても速いことがある。C=1 が紙の上では最安でも、実装では中くらいの C が勝つ、という感覚だ。

同じチャンク発想を、DeltaNet 本体へ伸ばす。

障害は単純だ。ただ足すだけの Linear Attention 用チャンク法を、差分で上書きする Delta 更新へそのまま持っていけない。

v_old = k_i @ S                  
u_i  = b_i * (v_i - v_old)

差し引くべき「今そこにある情報」を知るには、途中の状態が順番に要る。並べ方を数学的に書き直さないと、同じようには並列化できない。そこで著者は、デルタ更新の式を次の形から組み替える。

u=v_new-v_old
S_t= S_(t-1)+K.T@u
o=q@S_T

左の形は、ループが一周ごとに一つのデルタを出す。組み替えたあとの形は、次のように書ける。

S_t = S_{t-1}(I − β_t k_t k_tᵀ)  +  β_t v_t k_tᵀ
o_t = S_t q_t

この形だと、チャンク内の C 個のデルタをまとめて扱いやすい。

def chunk_delta_rule_forward(Q, K, V, beta, C):
		# L: sequence length, d: head dimension
		L, d = Q.shape
		# chunking
		Q, K, V = map(lambda x: x.reshape(-1,C,d), [Q, K, V])
		beta = beta.reshape(-1, C)
		K_beta = K * beta.unsqueeze(-1)
		V_beta = V * beta.unsqueeze(-1)
		
		# compute eq. 10 with vectorized forward substitution for fast inverse
		T = -(K_beta @ K.t()).tril(-1)
		for i in range(1, C):
				T[i, :i] = T[i, :i] + (T[i, :, None] * T[:, :i]).sum(-2)
		
		T += torch.eye(C)
		W = T @ K_beta
		U = T @ V_beta

		# chunkwise parallel. Eq. 8-9
		S = torch.zeros(d, d)
		O = torch.empty_like(V)
		
		for i in range(L//C):
				q_i, k_i, w_i = Q[i], K[i], W[i]
				u_i = U[i] - w_i @ S # the corrections, all of one chunk
				o_inter = q_i @ S
				A_i = (q_i @ k_i.t()).tril() #qk.t
				o_intra = A_i @ u_i # attention @ v (with corrections, so u)
				S += k_i.t() @ u_i # update state with addition 
				O[i] = o_intra + o_inter #update output with flash + recurrent
		return O.reshape(L, d)

ここまでで、最初の比較点に立てる。ふつうの Multi-Head Attention（MHA）と、DeltaNet 版 Transformer を横に置く。

Gated Delta Net

これで、キャッシュの一点を精密に書き換えられるようになった。新しい事実（新しいキー）ごとに、そこへ書いてあった古い情報を見て、注目したい新しい情報で置き換えられる。

足りない能力がある。「この事実を別の事実で上書きする」はできる。だが、話題が切り替わったときに複数の連合をまとめて消す、あるいは容量を空けるために記憶全体をじわっと薄める、は不得意だ。

もし記憶更新が、ただ足すだけの Linear Attention だったら、

「忘れる」を足すのは比較的簡単だった。前の状態をどれだけ残すか、という係数を一つ置けばよい。

S_old=cache
S_new=k@v
# cache=S_old+S_new
cache=alpha * S_old + S_new

これが Mamba-2 が持ち込んだ寄与に近い。前のキャッシュを減衰させ、新しい分をフルの強さで足す。状態が限りなく太るのを防ぐ。

毎ステップ、すべての連合を同じ比率で薄める——動的ではあるが一様な減衰——は実用的で、Mamba 系がやっていることだ。だが「どの連合がどれだけ大事か」の差は見ない。

一つだけ忘れたいときでも、全部が同じだけ薄まる。逆に Delta 規則は、一点の上書きは上手いが、残りをじわっと薄める手段がない。

Gated Delta 規則は、両方を足す。Mamba 側のゲートと、Delta 側の上書きだ。係数 alpha を置く。1 なら純粋な Delta、0 なら記憶をクリアする方向へ寄る。難しさは、前節と同じチャンク並列のまま実装することだ。

実装の骨格は、前節の DeltaNet の書き直しをそのまま使う。数式はほぼ同じで、足るのは一つ——前状態をどれだけ残すか、データ次第で 0 から 1 のあいだを取るスカラーだ。事実の書き換えと、記憶の太さの管理が同じ更新に載る。

KDA / Kimi Linear

研究は、一つの注意形式に賭け切るより、複数を一つの模型の中で混ぜる方向へも進んだ。Gated DeltaNet と Mamba を同居させる、といったハイブリッドだ。

Kimi Linear が目立ったのは、中心の主張が強いからだった。条件を揃えた比較で、フルの Softmax Attention を上回った、と。置き換え部品として、品質が良く、デコードのスループットが最大でおよそ6倍、と提示された。

Gated DeltaNet からの一歩は、減衰の粒度だ。状態全体を一つの alpha で薄めるのではなく、チャネルごとに別の減衰を学習する。「メモの行ごとに、忘れ方を変えられる」イメージに近い。

更新規則の骨格は似ている。コードは、次のように見える。

alpha を (チャンク数, C, 次元) へ reshape しているところが、論文のいちばんの寄与に対応する。メモリ減衰を、チャネル単位で触れるようにした。

DeltaNet Transformer の横に置くと、Kimi Linear は大きく三つ変わる。

  1. Multi-head Latent Attention（MLA）層をあいだに挟むハイブリッドにする。
  2. MLP を Mixture-of-Experts（MoE）に置き換える。
  3. alpha の射影を通じて、DeltaNet 側に容量を足す。

MLA と MoE の細部は後で触れる。いま押さえるのは、これが「とにかく大きくする」盲目的スケーリングではないことだ。足した容量には役割がある。チャネルごとのスケールが、忘れ方の解像度を上げる。

スケーリング則は無効になったわけではない。ただ、容量は「足せる場所」と「系が使える形」に置かないと効かない。ここまでの各段は、直前の設計が抱えた具体的な詰まりへ、容量を足している。

Kimi K3

KimiK3 の言語バックボーンは、上の Kimi Linear に近い。4層で一つのマクロサイクルを作り、それを23回繰り返す。各サイクルでは、3層が Kimi Delta Attention（KDA）、4層目が Multi-head Latent Attention（MLA）。最初の層だけ dense のフィードフォワード、あとの層は latent な Mixture-of-Experts だ。

Kimi Linear からの差分を一覧すると、一見控えめに見える。

  • 大幅なスケール増
  • 12層ごとの Blockwise AttnRes
  • MLA のクエリ LoRA と出力ゲーティング
  • 潜在空間で動く MoE
  • SiTU という活性化
  • Gated MLA

役割分担だけ先に読む。KDA は、サイズが膨らまない再帰メモリを担う。ところどころの MLA は、文脈全体への Softmax 的な精密検索を残す。固定メモだけではこぼれるものを、ときどき本式の検索で拾う、という同居だ。次の簡略図を、この分担の地図として見てほしい。

わかりやすい変更から行く。Gated MLA、潜在空間の MoE、SiTU 活性化だ。

Gated MLA は、「MLA が取ってきた特徴のうち、どれだけを本流（残差）へ通すか」を決める。入力から作ったゲートを、要素ごとに掛けて絞る。

ふつうの MoE では、ルータが各トークンを専門家の一部へ振り分ける。内積の似ている専門家へ送る、というやり方だ。KimiK3 の専門家は合計898。うち2つは共有で、どのトークンも通る。残る896から、トークンごとに16人を選ぶ。

専門家の中の活性化も変えている。昔ながらの「up に SiLU、ゲートと掛けて、down」ではなく、SiTU を使う。

d = x.shape[-1] // 2
gate = x[..., :d].to(torch.float32)
up = x[..., d:].to(torch.float32)
situ_a = self.beta * torch.tanh(gate / self.beta) * torch.sigmoid(gate)
if self.linear_beta is not None:
    up = self.linear_beta * torch.tanh(up / self.linear_beta)
return (situ_a * up).to(x.dtype)

共有専門家へ渡す前に入力を細い空間へ落とし（down 射影）、専門家の出力を足したあとで戻す（up 射影）——という経路もある。

推論では繰り返し出る摩擦でもある。専用に融合したカーネルがなければ、新しい活性化は昔の経路よりおよそ3倍遅い、となりうる。相殺の工夫の一つが、専門家を圧縮した潜在空間で動かすことだ。順伝播が速くなり、計算量もおよそ半分近くまで落とせる。

残りは、MLA のクエリ LoRA、出力ゲート、そして12層ごとの Attention Residuals（AttnRes）だ。AttnRes は推論の遅延をおよそ2%増やすが、利点が二つある。

  • より早い層の表現を選び取れる（残差が薄まりすぎる／隠れ状態が太りすぎるのを抑える）
  • 計算上、およそ1.25倍の得がある

AttnRes と MLA は、同じ根の困りごとに別方向から触れている。KDA は固定サイズの状態なので、必ず何かを捨てる。MLA はトークン列の文脈から拾い直す。AttnRes は、深さ方向——もっと手前の層が出した表現——から拾い直す。

AttnRes

この節は、原著でも @chloey3k の助けへの謝辞がある。順伝播では、入力が層の積み重ねを通る。各層は、注意（KDA か MLA）と、MLP か MoE、の組だ。

ふつう、次の層への入力は、最初の埋め込みと、ここまでの層出力を、同じ重みで足したものになる。どれも等しい、という前提だ。

$$h_l = h_1 + \sum_{i=1}^{l-1} f_i(h_i)$$

記号ではこう書く。h_i は層 i への入力。h_1 は、いま注目しているトークン（これまでの列の最後）の埋め込み。f_i(h_i) は層 i の出力（注意または MLP ブロック）だ。

問題は、選べないことだ。層の種類が違っても、同じ「全部足した状態」しか受け取れない。しかも純粋な加算なので、後ろの層が効かせるには出力をどんどん大きくしがちで、訓練が不安定になりうる。

AttnRes は、足し算の各項に専用の重みをかける。いまの文脈で効く層へ、より多くの票を渡せる。

$$h_l = \alpha_0 \cdot h_1 + \sum_{i=1}^{l-1} \alpha_i \cdot f_i(h_i)$$

重み alpha_i は、クエリとキーの内積から来る。クエリは層ごとに学習され、キーとバリューはより手前の残差状態から来る。スコアは合計1になるよう正規化し、その重みで手前の状態を混ぜる。

だからモデルは、「直前の層だけ」を見る必要がない。AttnRes は、手前の層出力への選択的アクセスを渡し、いまの計算に要る表現をクエリで取りにいける。

疑似コードは、同じ考えをブロック単位で書く。ここでブロックとは、デコーダ12層ぶんの注意と MLP の出力を足してまとめた、深さ方向の一つの要約だ。あとで AttnRes が混ぜる単位になる。

これを毎層やると、訓練も推論も高くつきすぎる。固定間隔の境界だけでやると、恩恵の大半を安いコストで取れる。KimiK3 では、その境界が12デコーダ層ごと。23個の4層マクロサイクル全体で、AttnRes ブロックは8つになり、推論の速さにも効く、と原著は書く。

block_attn_res でいちばん肝になるのは、おそらく次の部分だ。

V = torch.stack(blocks + [partial_block]) # [N+1, B, T, D]
K = norm(V)
logits = torch.einsum('d, n b t d -> n b t', proj.weight.squeeze(), K)
h = torch.einsum('n b t, n b t d -> b t d', logits.softmax(0), V)
return h

ここまでが、GPT-2 から KimiK3 までの一本道だ。

中心の変化は、単なる巨大化ではない。各段は、「何を倉庫に残すか」「倉庫をどう更新するか」「固定サイズでは保てないものを、どこから拾い直すか」のどれかを変えている。

KimiK3 は、次を同居させている。サイズが膨らまない再帰メモリ、ときどきの Softmax 検索、疎な専門家の容量、深さ方向の選択的アクセス。足した容量のそれぞれに、役割がある。

短い結論だけ置く。次元が固定された連想記憶には、追い出しの方針が要る。ただ足すだけの更新は、満杯のあと干渉を増やす。だから、ゲートやルーティングや減衰のような、学習された選択が要る。そして注意は、いまでも「何を読むか」を選ぶいちばん強力な手段の一つだ。
