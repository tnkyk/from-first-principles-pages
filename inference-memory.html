推論メモリと量子化, from First Principles

Hugging Face に「DeepSeek-V4-Flash」と出ると、カードには 13B activated・304B params・167 GB といった数字が並ぶ。読者の頭では「小さいから載る」「大きいから載らない」が同時に立ち上がり、どっちが正しいのか分からない。量子化を選ぶ画面では FP8 や 4bit が並ぶが、それが何を細かく・粗くしているのか、そして GPU に何を置けば生成が始まるのかが見えないまま、まずダウンロードが始まる。

メモリ不足や極端な遅さを「モデルが重すぎる」と一枚岩で扱うと、次の一手が流行の量子化名に預けられる。重み・KV・作業バッファのどれが封筒を食っているかを層で言えなければ、精度を落とすべきか文脈を短くすべきか、MoE の総パラメータと活性パラメータのどちらを見るべきかを自分で決められない。取り戻すのは予言ではなく、利用時メモリの勘定科目を自分で切る権利である。

この記事の狙いは、制約から機構を組み立て直すことだ。用語は必要が立ってから出し、各層を強制した問題の物語に沿って進む。

Hugging Face の DeepSeek-V4-Flash-0731 を開くと、カードに「304B params」と「167 GB」、ベンチ表の横には「はるかに小さい activated parameter count」と書いてある。同じ画面なのに、頭の中では「巨大だから無理」と「小さいから載る」が同時に立つ。どちらも部分的に正しい。欠けているのは、利用とは何をメモリに置く行為かという勘定科目である。

推論を始めるとき、機械が必要とするのは「モデルという抽象」ではない。少なくとも次の三つが、同じ封筒（RAM / VRAM）を奪い合う。

重みの常駐

学習済みのつながり——重み（parameters）——は、生成のたびにディスクから全部読み直すには大きすぎる。だから普通は、使う予定の重みをメモリ上に常駐させる。ここが第一科目だ。後で見るように、MoE では「計算に使う重み」と「置いておく重み」の数が一致しない。だが科目の名前は単純でよい。倉庫に置いた数値のバイト総量である。

KV キャッシュ

文章やツール結果が長くなると、注意は過去のトークンを何度も参照する。毎回ゼロから Key/Value を作り直すと遅すぎるので、推論系は過去分を KV キャッシュとして残す。これは重みとは別物だ。プロンプトが伸びるほど、会話が続くほど、考えるモードで出力が長くなるほど、この棚は太る。カードに「1M context」と書いてあっても、それは理論上の窓であり、あなたの封筒上の無料パスではない。

作業バッファ

前向き計算の途中には、層の入出力や一時テンソルが必要になる。バッチを大きくすれば膨らみ、実装やカーネルによってはピークが跳ねる。本稿では細部に入らないが、科目として忘れると「重みは入ったのに OOM」の説明が一つ欠ける。

DeepSeek-V4 系は、この KV 科目をアーキテクチャ側でも圧縮する（CSA / HCA）。だから「同じ百万トークン」でも、世代間で棚の太さが qualitatively 違う。だが入口の謎——カードの数字が矛盾して見えること——の第一解はそこではない。まず、載る／落ちるを一枚の「モデルサイズ」で語っていたこと自体が科目不足だった、と固定する。

三科目のうち、重み科目を Flash に落とすと、すぐに次の摩擦が出る。論文の DeepSeek-V4-Flash は 総パラメータ 284B、活性 13B と書かれる。0731 のモデルカードは 304B params と出し、構造は DSpark（投機的復号モジュール）付きだと言う。どちらを信じれば「小さい」のか。

答えは、問いを二つに割ることだ。

総パラメータ（格納）

総パラメータは、チェックポイントに含まれる数値の個数に近い。MoE では専門家（expert）が多数あり、トークンごとにその一部だけが選ばれる。選ばれなかった専門家の重みも、次のトークンで呼ばれる可能性があるので、普通は倉庫に置いたままにする。したがって、VRAM に載せる重みの第一近似は「活性 13B」ではなく「総 284B（や 304B）」側である。

ディスク上の 0731 がおおよそ 167 GB と見えるのも、この総数に、公式の低精度表現を掛けた結果として読むのが自然だ（後章）。BF16 で総数を一様に持つ想像は、すぐに数百 GB 級へ跳ねる。

活性パラメータ（演算）

一方、活性パラメータは、あるトークンの前向き計算で実際に触る重みの規模感である。Flash ではここが約 13B とされ、同じ世代の Pro（約 49B 活性）より一歩が軽い、という話になる。レイテンシや FLOPs の感覚、電気代の感覚は、しばしばこちらに近い。だが「GPU に何 GB 要るか」の第一近似を活性だけで取ると、倉庫を見落として楽観する。

0731 が 304B と表示される点は、preview の 284B に投機用モジュール等が乗ったリリース差分として扱えばよい。本稿の主張に効くのは小数点以下の B ではなく、格納のオーダーは総数、計算のオーダーは活性数という切り分けである。

「小さい activated なのに巨大チェックポイント」は矛盾ではない。広告の売り文句と、封筒の請求書が、別のメーターを指しているだけだ。

倉庫が総パラメータで決まるなら、次のレバーは個数を減らすことだけではない。1 個の数値を何ビットで持つかを落とせば、同じ個数でもバイト総量は Shrink する。これが量子化の中核である。

ここで、よくある誤解を一度潰す。重みは「0.0〜1.0 の小数第 1 位」ではない。正負どちらも取りうる実数であり、層によってスケールも違う。量子化が削るのは「小数の桁」というより、その実数を代表値へ丸める粗さと、それを格納するビット幅である。

ビット幅

概算の足場は単純でよい。重みのおおよそ GB ≈ パラメータ数 × bytes/param。

表現bytes/param（目安）284B 一様のとき（目安）
FP16 / BF162≈ 568 GB
FP8 / INT81≈ 284 GB
FP4 / 約 4bit0.5≈ 142 GB

実際のファイルはスケール係数や埋め込み、トークナイザ周辺、フレームワークのヘッダで上振れする。だがオーダー感を掴むには、この掛け算で十分なことが多い。

公式混合精度

DeepSeek-V4 系のリリースは、一様な FP16 ではない。公式の整理では、MoE の expert 側を FP4、その他の多くを FP8 とする混合が基本形とされる(*1)(*3)。0731 のカードが BF16 / F8 / I8 などを併記しつつ、実体サイズがおおよそ 167 GB なのも、「全部が FP16」ではないことの証拠として読める。

つまり Flash を「いまから 4bit 化する対象」とだけ見るのはずれる。すでに倉庫の大半は、低精度前提で詰まれている。コミュニティのより粗い量子化は、その上に乗る二段目になりやすい。

事後量子化

訓練後にビット幅を落とす古典が GPTQ や AWQ である(*4)(*5)。ローカルの「Q4 なら載る」は、多くの場合この系統の話だ。Flash にそれを適用するときは、公式が既に FP4 側へ寄せた expert を、さらに粗く丸めることになる。容量は下がるかもしれないが、品質の落ち方は「初めて 4bit にする 7B」とは別物になりうる。

シミュレーションを開く — 同じ総パラメータでもビット幅で重み容量が qualitatively 変わる

出口は楽観でも悲観でもない。量子化とは、パラメータ個数の話を、1 個あたりのビット幅の話へ翻訳する操作だ。Flash ではその翻訳の一部が、すでに公式チェックポイントに織り込まれている。

重み科目を FP4+FP8 まで落とし、マルチ GPU に分割して「載った」とする。それでも、長いリポジトリや reasoning_effort=max の長い思考で落ちることがある。これは Flash に限った呪いではなく、第二科目（KV）が伸びたときに必ず現れる形だ。

KV 成長

KV は「いま抱えている系列長」にほぼ比例して膨らむ。重みはプロンプトが短くても長くても同じ箱だが、KV は会話の履歴そのものだ。だから「同じ量子化の同じ Flash」でも、短い質問と百万トークン近くのエージェント軌跡では、封筒の中身が qualitatively 違う。

DeepSeek-V4 は CSA/HCA で KV を圧縮し、論文上は 1M 文脈で V3.2 比の数割〜1 割級まで棚を薄くできると主張する(*1)。これは第二科目へのアーキテクチャ介入である。サービング側では、さらに KV を FP8 で持つなどの精度レバーも併用される。いずれも「重みの Q4」とは別ノブだ。

KV 精度／圧縮

ここでの判断規則は短い。

  • 重みが載らない → ビット幅・並列分割・（MoE なら）総数の現実を疑う
  • 重みは載るが長いと死ぬ → KV と作業バッファを疑う
  • 短いのに遅い → 帯域やデコード、投機の成否など、容量以外の軸へ（本稿の外縁）
シミュレーションを開く — 重みを削っても文脈を伸ばすと KV が封筒を取り戻す

Flash のカードが 1M を謳うとき、それは「KV 科目が設計上かなり安い」という宣言であって、「あなたの 24 GB カードで百万トークンが無料」という宣言ではない。量子化で重み棒を短くしても、文脈スライダを右へ回せば、別の棒が封筒を埋め直す。

入口の奇妙さは、矛盾ではなかった。DeepSeek-V4-Flash は、計算の一歩（活性〜13B）としては小さく、倉庫（総〜284B／0731 では 304B 表示、ディスク〜167 GB）としては大きい。量子化は、その倉庫の bytes/param を動かす。文脈は KV を動かす。作業机は別途ピークを作る。

抽象の使い方

新しい「載らない／遅い」に出会ったら、まず用語ではなく科目を言う。重みか。KV か。作業バッファか。MoE なら、いま見ている数字が総数か活性数か。

壁に当たったときの型

  1. ディスク／VRAM の静的サイズが合わない → 総パラメータ × ビット幅（公式混合なら加重）を概算し直す
  2. 短い入力では生き、長いと死ぬ → KV（と KV dtype／圧縮）を疑う
  3. 公式 FP4+FP8 の上にさらに粗くする → 二段目の品質コストを別メーターで測る
  4. 並列で載せる → 分割は倉庫を複数封筒に分ける操作であり、通信と複製分も科目に入れる

Life placement

いま足りないのは、倉庫（重み）か、履歴棚（KV）か、作業机（バッファ）か。Flash を選ぶ／落とす／量子化する前に、その一文が言えるかどうかが、本稿の成功条件である。

判断規則

  1. 利用時メモリは少なくとも重み・KV・作業バッファの三科目で読む。
  2. MoE では格納＝総パラメータ、一歩の計算＝活性パラメータ。
  3. 重み GB の第一近似は「個数 × bytes/param」。Flash は公式に FP4+FP8 混合へ寄っている。
  4. 事後のより粗い量子化は二段目であり、容量と品質を別々に測る。
  5. 量子化で重みが載っても、文脈を伸ばせば KV が封筒を取り戻す。
